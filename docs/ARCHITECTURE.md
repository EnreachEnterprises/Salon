# Architecture

## Shape

npm workspaces monorepo. One app, two shared packages, one API added at B1.

```
salon/
  apps/
    mobile/        Expo React Native (SDK 58) + TypeScript, expo-router
    api/           Hono on Vercel (added at B1)
  packages/
    shared/        pure logic: money, metrics, time, zod schemas  (vitest)
    db/            Drizzle schema, migrations, RLS SQL, seed
  docs/
```

Dependency direction is one-way:

```
apps/mobile  ->  packages/shared
apps/api     ->  packages/db -> packages/shared
```

`packages/shared` imports nothing from `db` or `mobile`. `packages/db` never
imports React or mobile code. Mobile never opens a database connection — every
read and write goes through the API.

## Build order

Schema first, UI first, wire the backend last. The front end is built against
seeded data and a thin mock layer, so screens are proven before the API exists.
Block 1 produces an installable build; Block 2 replaces the mock with real data.

## Multi-tenancy

One database, many salons. Isolation is enforced twice:

1. **API layer** — every query is scoped by `salon_id` taken from the verified
   session, never from a client-supplied id, and role checks run at each entry
   point.
2. **Postgres RLS** — a second wall, per the design in
   `packages/db/sql/rls.sql`. The API sets `app.salon_id`, `app.profile_id`,
   `app.role` and `app.staff_id` per transaction with
   `set_config(name, value, true)`. A salon-scoped **permissive** policy is
   narrowed by **restrictive** staff policies. Never add a second permissive
   staff policy — permissive policies OR together and would widen access.

RLS is documented at P0 and applied at B1. Until then the schema is dev-only.

## Auth

Clerk handles sign-in (email OTP) and issues the JWT the API verifies. Clerk is
*only* an identity provider: tenancy and role are authoritative in
`salon_members` (uuid keys internally, `clerk_user_id` as the unique text link).
Using Clerk organisations as the source of truth would put authorization in two
places.

## Time and money

- Money is integer **paise**. No floats, no `numeric`, no rounding drift.
- The business day is stored explicitly as a `date` column on bookings,
  invoices and queue entries, so a 12:30am bill still belongs to the night
  before and reports never do timezone math.
- Salon timezone is `Asia/Kolkata`.
- Commission is `commission_bps` (500 = 5%), an integer.

## Live queue

No websockets, no realtime subscription. TanStack Query polls every 5 seconds
while the queue screen is focused, and stops when it is not. At salon scale
(tens of concurrent users) this is cheaper and far simpler than a realtime
channel, and it survives flaky mobile networks.

## Files and exports

PDF/CSV exports are generated in the API and stored in Cloudflare R2 with a
short-lived signed URL. Monthly reports are generated by Vercel Cron on the 1st
and emailed; weekly summaries go out on Monday; a headline figure goes by
WhatsApp.

## What not to "improve"

- Don't add realtime transport to the queue.
- Don't move authorization into Clerk organisations.
- Don't switch money to floats or `numeric`.
- Don't compute metrics anywhere except `packages/shared`.
- Don't duplicate the report logic for owner and staff screens.
